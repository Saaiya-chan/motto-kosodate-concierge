Ruri検索＋GeminiとGemini File Searchの比較
確認日：2026-10-21（このMacでの試作）

同じ11件の公式資料、同じGemini 3.5 Flash-Lite、各7問で比較。
うち6問がGoogleによる生成。自治体の空き・個別料金の1問は両方式共通のローカル判定なので速度集計から除外。
質問順による偏りを減らすため、構成の実行順を交互に変更。初回モデル読み込みは集計から除外。

                      File Search          Ruri＋キーワード補助＋Gemini
通常応答の中央値      5.30秒               1.32秒
通常応答の範囲        4.87〜5.67秒          1.26〜2.83秒
アプリ側検索          Google内部で不明     中央値20.7ms
入力トークン中央値    約9,189               約3,748

今回の構成では、Ruri側の通常応答の中央値が約4倍速かった。
Ruriのモデルはruri-v3-70m、CPUで常駐。既存索引がある通常のモデル読み込みは約3.7秒。初回の索引作成は別途約16〜17秒。
File SearchはGoogle側で検索・生成を一括処理するため、その内訳時間は判定できない。

内容確認
・制度説明、利用料の設定と所得に応じた減免、掃除の特例、産後ケアの出産後1年以内、2制度の目的の違いは、両方式とも主要な事実が資料と一致。
・未収録の翌年度予算と自治体の空き・個別料金は、具体的な金額・空き情報を捏造しなかった。
・File Searchは制度比較の回答冒頭に「確認できません」と付けてから説明する例があった。資料外予算の返答も質問に直接答えるより汎用の拒否文になった。
・Ruriは産後ケア対象時期の補足説明でも使った別チャンクのIDを付けなかった。資料外予算への回答にも、出典IDを付けないまま一般的な補足を加えた。全記述の出典を揃える点は改善余地がある。
・少数の架空質問を開発者が本文と照合した試験であり、正確性100%や専門家による独立評価を意味しない。

実装上の注意
・Ruri単独では料金の追質問を検索しきれなかったため、制度名・質問の補完と、キーワード検索2枠を併用。最大6本文をGeminiへ渡す。
・File SearchとRuri側ではチャンク分割、文脈による制度絞り込み、出典の出力形式が違う。検索モデル単体の性能比較ではなく、今回のアプリ構成の比較。
・Gemini 3.6 Flashは無料枠の日次20回上限に達したため、主比較は両方とも3.5 Flash-Liteで実施。初期の3.6の部分的な結果は別ファイルに保存し、上記集計には混ぜていない。
・Googleの制限・負荷で速度と利用可否は変動する。

使う
画面の回答モードで「Ruri検索＋Gemini」を選択。現在の保存済みモデルはgemini-3.5-flash-lite。
APIキーと既存のGoogle資料集は継続使用。Ruri経路は検索済み本文と会話をGoogleへ送信する。
